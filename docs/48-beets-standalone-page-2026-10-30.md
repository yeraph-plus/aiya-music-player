# 整理库独立单页：查询 → 存为歌单（docs/48）

> 状态：**已实现**。日期：2026-10-30。前置：docs/33（术语与"beets 是增强不是依赖"）、  
> docs/43（§1.1 "整理输出 radio 是纯装饰"）、docs/47（模块解耦）。

---

## 0. 一句话

beets 的东西从"扫描入库页的第二段"搬成**侧栏独立的一页**，这一页只做两件事：  
**跑一次 beets 查询**、**把结果存成应用内歌单**。旧的那套（导入面板 / 维护四件套 /  
插件市场 / 曲库目录里的「整理输出」单选）整体下线。

删掉 7 个文件约 1730 行，新增 1 个视图 + 1 个 store。

---

## 1. 为什么搬走，而不是就地改

### 1.1 曲库目录里的「整理输出」单选是**假控件**（docs/43 §1.1 的结论）

那条链路走查下来：radio 写的是应用设置 `beets.targetRoot`，`effectiveTarget` 只用来  
渲染选中态和一句 toast；真正决定文件落点的是 sidecar `config.yaml` 的 `directory`，  
它在**首次** `ensure_config()` 之后再也不更新。也就是说用户切换 radio 之后 beets 的  
实际输出不变，而 toast 说"已指向 X"——**是谎报**。

这一批直接把它删了（连同它背后的 `beetsConfig` store）。曲库页是**本应用**的设置面，  
不该出现另一个库的配置项；这条也正好落在 docs/47 的解耦方向上。

### 1.2 两个"库"同页，术语和状态都打架

- 术语：曲库（`tracks` 表）与整理库（beets 的库）都叫"库"，页面上并排出现时  
  用户无法从按钮文字判断它动的是哪个；
- 状态：扫描跑着的时候整理库那一段全是灰按钮，但两者其实**没有共享任何资源**  
  （两个 SQLite 文件、两把锁、两条进程链），灰只是因为它俩恰好写在一页里。

分开之后两边各自成立：曲库页只管"我的曲库怎么进来"，整理库页只管"我的另一个库里  
有什么、要挑哪些进歌单"。

### 1.3 原来的前端大半是集成测试期留下的

`ImportPanel` 556 行里有大量用于验证协议的命令入口（预览/应用/取消/待整理目录…），  
维护四件套（登记/重写标签/查重/重排文件）和插件市场同理。它们验证的是**工具能不能  
干活**，不是用户日常要做的事。这批把它们从 UI 摘掉，后端命令保留（见 §4.3）。

## 2. 这一页长什么样

三块，自上而下：

1. **组件状态**：没装 → 一句说明 + 两个安装按钮（快速安装 / 免安装包）；装了 →  
   一行库状态（库文件路径 / 入口来源 / 插件可用数 / 库被占用时一个角标）；  
   协议指纹不匹配 → 明确的"版本不一致"警告 + 安装按钮（不给查询入口）。
2. **查询**：两种模式互斥——
   - **条件**：字段下拉（来自 `beets_fields`，插件写的 flexible 键会标「插件」）+  
     算子下拉（按字段类型收窄）+ 值。多条之间是「并且」。
   - **原始语法**：beets 自己的查询串，逃生口。  
     右侧是条数上限与「查询」按钮。
3. **结果**：每行标「已入库 / 未入库」，未入库的行**压暗且勾选框禁用**；  
   工具条吸顶，显示"已选 N 首 · 本页 M 首不在曲库"+「存为歌单」。

## 3. 三个设计决定（都是"为什么不那样做"）

### 3.1 未入库的命中**不造行**，且要在**查询后**就标出来

beets 库里可能有用户还没扫描进曲库的文件。可以有两种处理：

- 给它造一条假曲目 → 歌单点开就是"文件缺失"，把问题推迟到最尴尬的时刻；
- 直接丢掉 → 用户点了全选、存完发现"我选了 50 首怎么只进去 30 首"，没有解释。

选的是第三条：**逐行标注 + 不可选 + 计数**。为此加了宿主命令

|                                          |                  |
| ---------------------------------------- | ---------------- |
| \`tracks_resolve_paths(paths) -> (string | null)[]\`（同序等长）。 |

为什么不把 `track_id` 直接塞进 `BeetsQueryHit`：那是 beets 模块的 DTO，它读的是另一个  
库，那边不该出现本应用的行 id（docs/47 §2 的方向约束）。由**宿主**在命令层补一次  
翻译，模块仍然只发路径——解耦面没有变宽。

归一化只有一处：`aiya-data::repo::path_key`（分隔符统一 + 小写）。`aiya-beets-store`  
里有一份同口径的 `path_key`，两边**不能互相依赖**，所以用一条测试（`beets.rs::
path_key_agrees_across_crates`）拿同一批样本把两份实现锁在一起——漂移的症状不是报错，  
而是"增强结果一条都对不上曲目"。

### 3.2 存歌单只保留**一条**创建路径

曾经写过一个 `playlist_create_from_paths(name, paths)`（在宿主里解析路径 + 建歌单 +  
回带未入库统计），后来删了。理由：

- 它和已有的 `playlist_create(name, trackIds)` 语义重叠，两份实现迟早漂移；
- UI 为了"事前标注未入库"仍然要解析一次路径，那条命令就成了第二次解析；
- 歌单创建多一个入口 = 同名合并/去重规则要在两处各自解释一遍。

现在是：UI 查询时解析一次（拿到每行的 `trackId`）→ 保存时把已选的 id 交给  
`playlist_create`。同名歌单是**合并**（id 由名字派生、重复曲目跳过），弹窗里写明了  
这一点，避免用户以为点两次会得到两个歌单。

### 3.3 维护四件套与插件市场：命令留着，入口不搬

`beets_adopt`（登记进整理库）/ `beets_update`（按文件标签重写）/ `beets_duplicates` /  
`beets_move` / `beets_plugin_catalog` / `beets_plugin_install` 这些命令都还在，且仍在  
`lib/ipc/client.ts` 里（契约测试 `registered_commands_have_callers` 要求每个注册的  
命令都有调用点）。

不搬的理由：它们**改用户的文件**（或者改 beets 的配置/环境），和"查一批歌存成歌单"  
是两个心智模型。放在同一页会出现"我只是想查个 bpm 结果旁边一排危险按钮"。  
哪天真要做，应当是独立的一页（比如"整理库维护"），而不是塞回这一页。

`beets:maintenance` 的事件订阅也跟着下线了（`boot.ts` 里有注释）。这是一处**必须  
成对**的改动：订阅留着而没人触发是死代码；反过来哪天恢复命令入口却忘了恢复订阅，  
界面会永远转圈。

## 4. 解耦复核（相对 docs/47 的增量）

| 维度                     | docs/47 之后               | 本批之后                              |
| ---------------------- | ------------------------ | --------------------------------- |
| 代码依赖                   | 核心 crate 不依赖 beets       | 不变（`check:boundary` 每次 verify 都报） |
| 数据模型                   | 应用库里没有 beets 表           | 不变                                |
| 运行时                    | beets 不碰 `scanning`      | 不变                                |
| **应用 UI 是否写 beets 配置** | **仍有**（曲库目录的「整理输出」radio） | **已删**——应用侧不再有任何写 beets 配置的入口     |

新增的接触面只有一处、且是单向只读：`tracks_resolve_paths` 读 `tracks` 表，w  
beets 模块完全不知道它存在（是 UI 调的）。

## 6. 验证

### 6.1 新增的 e2e（`ui/e2e/route.spec.ts`）

| 测试                    | 守的是                             |
| --------------------- | ------------------------------- |
| 整理库是侧栏独立的一页           | 可达 + 侧栏高亮**恰好一个**               |
| 未装 beets 时只给安装引导      | 不给查询入口；导入面板/维护折叠/市场都不存在         |
| 查询 → 未入库行不可选 → 全选存为歌单 | 未入库行禁用；全选只覆盖已入库；存完侧栏出现该歌单、按钮回禁用 |
| 曲库目录行不再带「整理输出」单选      | 那条假控件不会被人"顺手加回来"                |

删掉的旧断言（对应 UI 已下线）：待整理目录引导、整理库四件套、插件市场，以及  
"扫描入库页两组卡片"改为"只剩曲库一组"。

### 6.2 e2e 里翻出三处**既有**问题（都不是这批引入的）

跑全量 e2e 时有两条用例红，根因相同：**e2e 不在 `verify` 里**（`verify` 只有  
svelte-check + 6 个 Rust/Python smoke），所以 docs/46 那轮改了侧栏与频谱设置  
之后，UI 行为回归没有任何门禁看着。

| # | 症状                              | 真因                                                                          | 修法                                             |
| - | ------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| 1 | `一级路由逐个可达` 稳定 30s 超时            | 用例把「设置」排在「正在播放页」之后，而那一页**侧栏整体退出**（docs/46 §5.2）→ `.sidebar .nav-item` 永远不可见 | 把正在播放页挪到数组末尾；"整页之后回列表"的检查改挂到「设置」那步（最后一个有侧栏的页面） |
| 2 | `正在播放页：两栏沉浸` 同样超时               | 同上——它从那一页直接点侧栏去设置                                                           | 先 `Escape`（keyboard.ts 给这一页的明确退路）再点侧栏          |
| 3 | 同上，改成 Esc 后卡在开关名                | 设置里一个「频谱可视化」被 docs/46 §5 拆成「背景动态频谱」/「正在播放页频谱」                               | 用新名字                                           |
| 4 | 最后一条断言 `.ambient-spectrum` 恒为 0 | 那个 canvas 现在**只在 WebGL 不可用的 2D 兜底路径**上存在 → 断言"为 0"是真的，但它什么都没验               | 改盯页内 `.np-spectrum`（`npSpectrum` 开关派生），先 0 后 1 |

第 4 条值得单独记：**一条恒真的断言比没有断言更贵**——它让"这个功能没被验证"  
看起来像"这个功能被验证过了"。

> 建议（本次未做）：把 `npm --prefix ui run test:e2e` 加进 `verify`。代价是  
> +1~2 分钟和一封 Edge，换来的是 UI 行为回归不再靠人想起来跑。

### 6.3 新增的 Rust 单测

- `repo::path_key`：分隔符两种写法落到同一个键、重复归一等价；
- `track_ids_by_paths_matches_after_normalizing`：原始路径（正斜杠、大小写不同）  
  也能换到 id；查不到返回空表而不是报错；
- `resolve_paths_aligned_keeps_order_and_marks_misses`：**同序等长**、未命中是 `None`  
  而不是造一条、空输入是空结果；
- `beets::path_key_agrees_across_crates`：两个 crate 的归一化口径锁死。

## 7. 没验到的 / 已知取舍

1. **真机能装的 beets 库没跑过这一页的完整链路**（查询 → 存歌单）。e2e 走的是 mock；  
   sidecar 侧的 `query` 由 `smoke:enrich` 覆盖（真 sidecar、真库、38 条消息），  
   但"UI 的规则组装 → 工具侧求值"这一跳是靠两边各自的测试拼起来的，没有端到端。  
   要补的话得有一个装了 beets 的干净机。
2. **本次没有"存完跳到新歌单"**。留在原地是刻意的（可能想连着存几个不同的筛选结果），  
   代价是用户要自己去侧栏点。如果实际用起来别扭，改 `beets-query.svelte.ts::save`  
   最后一行调 `playlists.open(id)` 即可。
3. **`raw` 模式下不解析回带字段**：只带 title/artist/album。解析别人的 DSL 等于写第二份  
   实现，不值得。
4. 维护四件套的**后端命令现在没有 UI 入口**。它们仍会被 `check:dep`/契约测试照看  
   （必须有调用点），但"能不能真的跑通"只有 `smoke:maint` 在守。
