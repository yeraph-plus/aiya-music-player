# ADR-0003：播放状态机在 Rust，UI 只读

- 状态：Accepted
- 日期：2026-10-23

## 背景

现版状态机在 Electron 主进程，音频执行器在渲染层。为了跨进程一致，引入了 token、广播、`did-finish-load` 补发、多窗口假设。这些复杂度来自“状态与声音不在同一生命周期”。

## 决策

`PlayerActor` 在 Rust host 内运行，独占队列、索引、重复、随机排列、播放状态、位置、音量、速率、错误。UI 通过命令改变状态，通过事件接收 `PlayerSnapshot`；UI 不判断“下一首是谁”，不维护第二套队列。

## 后果

正面：

- 状态与音频同域；token/generation 只用于音频装载，不用于跨进程状态修复。
- 托盘/SMTC/全局快捷键/窗口关闭都能控制同一个 Actor。
- UI 重载/崩溃不影响播放；重连只需拉快照。
- 队列/恢复/历史可以在同一事务边界持久化。

负面：

- 前端不能做“乐观播放”；按钮反馈要等事件（可用 pending 状态缓解）。
- 队列编辑/选择解析要走命令，IPC 次数增加；用批量命令/分片缓解。
- 需要把现版 536 行 `player.ts` 与测试翻译到 Rust。

## 约束

- `PlayerState` 不包含完整队列；队列用 `queue_slice` 分片拉取。
- 每个 `load` 带 `generation`；旧 generation 的事件丢弃。
- 状态事件带 `revision`/`seq`；UI 丢弃乱序。
- UI 只保留 `pending` 覆盖层（拖动 seek、输入中的音量），不拥有权威状态。

## 否决的替代方案

1. **状态留在前端，后端只做音频**：托盘/SMTC/窗口关闭无法可靠控制；UI 重载会丢队列。
2. **前后端双状态 + 同步**：回到现版 token/补发的复杂度，且更容易漂移。
3. **每个窗口一个状态机**：多窗口必然分叉；单窗口也不利于托盘/SMTC。
