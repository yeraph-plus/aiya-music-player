# beets 集成是否要"音频 host 化"——独立常驻子进程调研

> 状态：**调研完成，建议拍板：不迁，维持现架构（v2 短进程模型）**。日期：2026-10-30。
> 问题（用户提出）：是否应该把 beets 集成部分从当前项目里，用类似 `aiya-audio-host`
> 的方式生产为独立子进程，内部单独维护、单独管理？
> 前置：docs/33（两侧分离架构，M1–M4 已落地）、docs/41 §10（协议 v2 已落地 + 第一轮
> 评审结论"基于现状迭代"）、ADR-0002（音频助手独立进程）。
> 本文只做架构判断，不改代码。

---

## 1. 一句话结论

**不建议。** 音频 host 独立成进程的三条理由（实时线程隔离、崩溃隔离、驱动/COM 异常
不拖垮应用）对 beets 一条都不成立；而 beets 集成真正的痛点（会话竞争、取消、单写者、
对账、断点恢复）在 docs/33 拍板 + v2 加固轮里已经**就地修完**，且那一轮的每一刀都
落在局部——架构没有提出任何"只有换形态才能解"的问题。迁了是多一个协议、多一个
exe、多一层版本协商，换不来任何一个可感知的改善。

---

## 2. 先澄清对象：beets 集成今天的四块，谁已经"独立"了

"beets 集成部分"其实是四块，独立程度差别很大：

| 块 | 位置 | 规模 | 独立程度 |
|---|---|---|---|
| ① Python 工具（beets 全部领域知识） | `beets-tool/`，独立 pip 包 | ~2000 行 + 测试 | **已经是独立进程 + 独立发布**（`beets-v*` tag，两轨安装） |
| ② 协议 | `v2.schema.json` + 双侧镜像 | 字节钉死 | 已是版本化契约 |
| ③ Rust 会话客户端 | `crates/aiya-beets-client` | 1441 行 | 工作区内 crate，**不依赖 Tauri**，可独立测试 |
| ④ 宿主编排 | `src-tauri/src/beets.rs`（1743 行）+ refresh 的 beets 段 | 发现、安装、DTO、事件转发 | 在播放器进程内 |

**关键事实：beets 侧（①②）的隔离程度已经超过音频侧**——`aiya-audio-host` 是工作区
内部组件、随播放器安装包一起发布，从来没有独立版本号；而 beets-tool 有自己的
pyproject 版本、自己的 tag、自己的两条安装轨道。所以"像音频 host 那样独立"对 beets
而言**不是升级，反而是把①的独立发布降级成工作区内部件**。

真正的问题因此收窄为：**③④（播放器内的 Rust 编排层，合计约 3200 行）要不要搬出去，
变成一个常驻的 `aiya-beets-host.exe`（工作区内、随播放器发布），播放器经命名管道
与它说话？** 下文全部针对这个问题。

## 3. 音频 host 为什么存在——三条理由逐条对照 beets

ADR-0002 的决策依据，与 beets 工作负载的对照：

| ADR-0002 的理由 | 音频侧的事实 | beets 侧的事实 | 成立？ |
|---|---|---|---|
| **实时线程隔离** | WASAPI 独占/低延迟线程不能与 UI/DB/GC 同进程 | 批处理操作（导入/对账/整理），延迟以秒计，用户在等进度条 | ❌ 无此需求 |
| **崩溃隔离** | 解码器/COM/驱动异常会拖垮整个应用；音频崩溃不能带走播放器 | sidecar 本来就是独立进程；Rust 客户端的失败模式（spawn/超时/协议）已映射为稳定错误码 | ❌ 已经由短进程模型提供 |
| **可独立诊断/自检/重启** | `--selftest`、独立日志、重启恢复播放位置 | sidecar 有 doctor/status；重启 = 下条命令起新进程，零成本 | △ 已有，形态不同 |
| （隐含）**常驻才有意义** | 播放是连续流，进程必须活着 | 一命令一进程，进程生命周期 = 命令生命周期 | ❌ 常驻对批处理是纯负担 |

再看"被监督的成本"。音频 host 模式的不可能免费（ADR-0002 负面栏原文）：多一个 exe、
supervisor、握手/心跳/重连逻辑、打包/签名/杀软兼容。实际代码：`sidecar.rs` 575 行
（supervisor + 管道帧）+ host 399 行 + `pump.rs` 667 行 + 协议 crate + 心跳线程
（2026-10-28 还修过"心跳必须独立于引擎初始化"的深坑）。**这套机器是为了"永远不许
死"的进程设计的；beets 的进程是"死了正好、下条命令重来"的，给它套心跳/重连是把
为另一个问题设计的方案硬搬过来。**

## 4. 变体评估

| 变体 | 内容 | 净代码变化 | 净收益 | 判断 |
|---|---|---|---|---|
| **A：现状**（v2 已落地） | 播放器内 Rust client + 短进程 Python | — | — | **建议维持** |
| **B：beets-host 宿主** | 新增常驻 `aiya-beets-host.exe`（工作区内、随播放器发布），③④搬入；Python 侧维持短进程 | **净增**：host 壳 + 管道协议 + supervisor 变体 + 打包签名 ≈ +1500~2000 行，换走 ~3200 行，但播放器仍需 ~300–500 行管道客户端 | 见 §5，逐条为空或负 | ❌ |
| **C：完全服务化** | B + Python sidecar 也常驻（host 内管理，心跳/TTL/续跑全在 host） | 在 B 之上再加 ADR-0005 全套机器（BWM 为常驻模型付的那套） | 锁-by-death 设计作废；spawn 省下的 ~300ms 对批处理无感 | ❌❌ |
| **D：host 随 beets-tool 发布** | Rust host 的构建/发布挂到 Python 包轨道 | beets-tool 发布流程引入 Rust 交叉编译工具链 | 只对"多消费端共享 host"有意义，而该前提不存在（§6） | ❌（前提缺失即无意义） |

## 5. 变体 B 的候选收益逐条盘点（诚实清单）

把能想到的"搬出去的理由"全部列出来，逐条对照现状：

1. **"播放器崩溃时在途操作会丢" —— 不成立。** 代码里没有任何 job object /
   kill-on-close（`CREATE_NO_WINDOW` 是唯一的创建标志）；播放器死亡 → sidecar 的
   stdin 断开 → 主循环在**当前命令跑完后**才处理 EOF 哨兵 → 在途的 apply 照常完成、
   断点落账、下次刷新对账。唯一损失的是发不到已死 UI 的事件，而 UI 已经死了。
   变体 B 的 host 确实也能活过播放器崩溃——但它活下来的收益是零。
2. **"每 30 秒起一次 Python 太浪费" —— 不成立。** refresh 管线是事件驱动的：
   `should_run_beets(Timer, …)` 先看磁盘扫描有没有变化（测试原话"定时刷新该先看
   磁盘变没变"），没变化不跑 beets 段。不存在周期性 spawn；单次 ~300ms–1s 的
   起进程成本摊在"用户点了整理/磁盘真的变了"上，本就是工作流的一部分。
3. **"播放器不该知道 beets 怎么装" —— P1 已经达成，且剩余知识是播放器的本分。**
   docs/33 M1–M4 已把 config 生成、插件清单、解释器探测、pip 编排全部搬进
   beets-tool；`beets.rs` 剩下的是发现（找到工具）、下载解压（安装轨道的 UX）、
   DTO 映射、事件转发——Cargo.toml 注释即拍板原文："宿主这里只负责「怎么找到它」
   和「结果怎么入库」"。搬给 host 之后，安装按钮/进度事件/设置页这些 UX 代码
   还得留在播放器里并新增一条转发链，知识只是挪位置，不消失。
4. **"边界要更硬" —— 已经是编译期事实。** `check-boundary.mjs` 在构建图层面禁止
   核心 crate 依赖 aiya-beets-client（"没装 beets 也能完整播放"是 cargo 就能证明
   的，不靠进程隔离加固）。进程化不会让它更真。
5. **"单写者更好管" —— 反而变差或持平。** 现状：会话槽（实例内）+ v2 文件锁
   （跨实例，进程死锁自动释放）。beets-host 若按播放器实例各起一个，多实例问题
   原样存在；若做成单例服务，就要引入服务生命周期管理（按需启动、崩溃重启、
   升级换版）——正是 BWM ADR-0006 记录的三次故障发生地。
6. **"中间人风险" —— 这是最重的一条反对理由。** docs/41 §2 刚论证过：BWM 的
   两容器 + HTTP 桥形态摔了三次（插件版本漂移、配置耦合、桥的序列化与超时失控），
   我们的优势就是链路最短（播放器 ⇄ 工具，一份版本化协议）。变体 B 把链路变成
   播放器 ⇄ host ⇄ 工具：**两份协议、两次版本协商、三个组件的版本矩阵**。第二份
   协议（播放器⇄host）是全新的漂移面，它的存在理由却只是"代码想换个进程住"。

净结论：B 没有解决任何 A 未解决的问题，同时新增一类 A 没有的问题。

## 6. 什么时候应该重开这个议题（可证伪的触发条件）

以下任何一条**真实发生**（而不是预期），就值得把变体 B/C 重新上桌：

1. **出现第二个消费端**：远端/移动 UI、CLI 工具、或多实例协作需要共享同一套
   beets 会话与锁——共享服务（host 单例）从"纯开销"变成"唯一合理解"。
2. **beets 侧出现常驻需求**：例如 watch-import、实时对接下载器（BWM 的 SLSKD
   集成形态）、或超大库上 dump 的常驻缓存被证明必要——那时 Python 常驻 +
   ADR-0005 心跳机器才有回报，且 host 是承载它的自然位置。
3. **安装/升级管理复杂化**：多版本并存、灰度回滚、自动迁移编排——host 作为
   "组件管理器"的形态开始还债。
4. **实测推翻 §5.2**：如果未来 refresh 策略改成更激进的周期对账，spawn 成本
   占比被实测证明显著（当前无此证据；重扫 1846 首 60ms、dump 有 180s 上限）。
5. **beets.rs 膨胀失控**：1743 行已是宿主第二大模块。注意——这条的解法**不是**
   进程化，而是 §7 的模块拆分；只有当"拆模块"已经救不动（跨模块共享状态、
   测试需要起真进程才能覆盖编排逻辑）时才升级为形态问题。

## 7. 变体 A 内部值得做的（把"想重构"的冲动导流到正确粒度）

- **beets.rs 拆分**（纯模块化，不动架构）：`discovery.rs`（入口发现 + 探测）、
  `install.rs`（两轨道下载/校验/安装器超时与收尸）、`session_glue.rs`（run_session
  + 事件通道约定）三个文件，beets.rs 只留 DTO 映射与命令包装。触发点：下一次
  要往 beets.rs 加功能时顺手做，不值得单独开批。
- **观察项**：ops.jsonl 审计日志目前没有消费者（P1-5 任务注册表的预留）；等它
  长出 UI 时，评估是否需要 host 形态——那是 §6.1 的前兆信号之一。
