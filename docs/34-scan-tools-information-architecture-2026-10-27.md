# 扫描入库页的信息架构重整

> 状态：**已落地（2026-10-27）**。起因是使用者对 M4 实现的一句"不知道怎么评价"。
> 相关：docs/29（这一页从设置页拆出的来历）、docs/33（beets 分离产生"两个库"）。

## 1. 起因：三条评审意见

1. beets 的导入目录自己有一套功能线，建库基线这些维护功能又是另一套东西。
2. 播放器自带的入库（一次性线程）与 beets（持久会话）能否共用同一套
   "任务派发 → 处理 → 结果确认 → 回调"管线。
3. 诊断与日志大部分没用；快捷键冲突这类专门检测，应该由对应功能块与
   对应设置界面自己携带，而不是各做各的。

## 2. 核查结果

第 1、3 条成立，且有代码层面的证据；第 2 条要拆开看。

### 2.1 第 3 条：两处是纯重复，不是"没用"而是"多余"

`SettingsPanel.svelte:78` 的注释自己写着：

```ts
// 快捷键区的即时冲突提示（诊断块的"快捷键冲突"已随分区搬去扫描入库页，
```

搬动方向反了——本该删掉旧的那份，结果在新页面又写了一遍。同理，
`LibraryTools` 底部的「beets 工具」块与诊断区「beets 集成」块展示的是同一批
字段（版本 / 入口 / 库根 / 插件健康度），只是排版不同。

另外四块属于"只在出 bug 时才有意义"的自检：`媒体流`（`streams.active`
正常恒 0，是协议层泄漏检测）、`最近查询`（SQL 性能排查）、`系统媒体控制`、
`系统集成`（防休眠 / 托盘，都是设置页开关的实际状态）。放在主路由上，
等于让用户每天读一遍开发者日志。

### 2.2 第 1 条：根因是"按组件排"而不是"按对象排"

这一页此前是七个并列段落，分别属于三条互不相干的功能线。术语打架的根源
是**它们背后其实是两个库**：

| 你以为是一个东西 | 实际是两个 |
|---|---|
| 「扫描目录」 | 写播放器自己的 SQLite（`tracks` 表） |
| 「导入目录」 | 写 **beets 的库**（另一套目录 + `library.db`），再对齐回曲库 |
| 「库根」 | beets 的 `library.directory` |
| 「曲库」 | 播放器的 tracks 表 |
| 「重新扫描」 | 重读文件元数据，建索引（只读） |
| 「刷新标签」 | 让 beets 按 `path_formats` **重写文件标签**（写盘） |

最后一行是最危险的：两个名字听起来都是"重新读一遍"，实际一个只读、
一个会改文件。

### 2.3 第 2 条：能统一外壳，不能统一数据

五条任务线的现状：

| 线 | 派发 | 终态判定 | 取消 |
|---|---|---|---|
| 扫描 | `library_scan` | `done` 事件 | `library_scan_cancel` |
| beets 导入 | `beets_preview` / `beets_apply` | `done` / `applyDone` / `sessionEnd` | `beets_cancel` |
| beets 维护 | 同上（共用会话） | 同上 | 同上 |
| 安装 | `beets_install` | `done` / `error` | **没有** |
| 刷新 | 内部线程 | `libraryRefreshed` | **没有** |

内部模型确实不同，而且不该被拍平：

- **扫描是无状态进度流**：每条事件带全量计数快照，重复/丢一条都能恢复，
  "终态"只是最后一个快照。
- **beets 是有状态机 + 累积领域数据**：`preview → apply → syncing`，
  而且 `album` 事件要一条条累积成列表（专辑、候选、决策）。把它塞进通用
  任务模型，结果是一个既不能渲染专辑又不敢丢事件的四不像。

所以这一轮**只做界面分组，不动任务层**。真正该统一的是另外三件事，
它们现在做不到：

1. 扫描跑着时 beets 按钮只是变灰，用户不知道原因（其实是 `scanning` 互斥）
2. 安装卡住只能杀进程
3. beets 维护失败只写进 `maint.error`，页面一刷新就没了

这三件的解法是**任务登记表**（`job_id + kind + 可取消` + 一个前端
`TaskView[]` 投影），不是"统一成一条管线"。留给下一步。

顺带说明：M4 其实已经统一了一半——所有命令收尾都走同一条刷新管线
（`refresh::spawn`），不再各自 dump + sync。

## 3. 方案：两个名字，两组，一个折叠

### 3.1 命名

| 旧 | 新 | 为什么 |
|---|---|---|
| 曲库 / 库根 | **曲库** / 整理库根 | 两个都叫"库"是上一轮术语打架的根源 |
| （beets 那边） | **整理库** | 它管的是标签与文件结构，"整理"是用户能理解的职能 |
| 建库基线 | **登记到整理库** | "基线"是自造词，实际动作是"把曲库已有曲目写进 beets" |
| 刷新标签 | **重写文件标签** | 与曲库的"重新索引"区分：这个会写盘 |
| 整理文件 | **重排文件位置** | 说清动作是移动/复制，不是"整理一下" |
| 导入整理（beets） | **导入新文件夹** | 面板对象是"一个新文件夹" |
| 从 beets 同步 | **从整理库对齐** | 与自动刷新是同一条管线，说法要一致 |

### 3.2 结构

```text
扫描入库
├─ 曲库（必有）
│   ├─ 曲库目录（textarea，一行一个）+ 添加目录 / 立即索引
│   ├─ 索引进度（跑的时候才出现）
│   └─ 概况一行：1472 首 · 96 专辑 · 12 位艺人 · 时长 · 离线 N
│      自动刷新一行：每 30 秒 · 上次 12:15 无变化
└─ 整理库（可选）
    ├─ 工具状态一行（未装 → 两个安装按钮；装了 → 版本 / 整理库根 / 插件摘要）
    ├─ 导入新文件夹（预览 → 应用）
    └─ 整理已有曲目 ▾（登记 / 重写标签 / 查重 / 重排，默认收起）
高级与诊断 ▾（版本 / 平台 / schema / 数据目录 / 最近错误）
```

两条规矩：

1. **beets 未装时这一段收成一行提示 + 两个按钮**，导入面板与四件套整段
   不渲染。docs/33 说"beets 是增强能力不是播放依赖"，以前只是代码上成立，
   界面上不成立（十几个灰按钮）。
2. **任务状态跟着发起它的对象走**（索引进度在曲库段，导入进度在整理库段），
   不再集中到"任务区"。集中式的任务面板要等任务登记表做完再上，
   现在硬凑会同时得罪两边。

### 3.3 下放与删除清单

| 块 | 原位置 | 现在 |
|---|---|---|
| 快捷键冲突 | 诊断区 | **删**（设置 → 快捷键本来就有） |
| beets 集成 | 诊断区 | **删**（整理库段本来就有） |
| 媒体流 | 诊断区 | **删**（协议层泄漏自检，看日志） |
| 最近查询 | 诊断区 | **删**（SQL 性能排查，看日志） |
| 系统媒体控制 | 诊断区 | 设置 → 系统 → 系统媒体键，说明末尾一行「当前：已生效」 |
| 系统集成（托盘） | 诊断区 | 设置 → 系统 → 托盘开关，说明末尾一行「当前：已创建」 |
| 防休眠 | 诊断区 | **删**（无对应开关，极少出问题） |
| 自动刷新 | 诊断区 | 曲库段（它就是那条管线） |
| 库规模 / 时长 / 离线 | 诊断区 | 曲库段概况行 |
| 版本 / 平台 / schema / 数据目录 / 最近错误 | 诊断区 | 折叠「高级与诊断」 |

## 4. 一处数据补丁

`ScanProgress` 加了 `missing` 字段（`#[serde]` 默认 0，只在 `done` 那一刻
有值）。原因：曲库段要一直显示"离线 N"，而它原来只活在 `ScanResult` 里，
UI 拿到结果后没有地方存。放进进度事件后，前端 `ScanProgressView` 加
`updated` / `missing` 两个字段即可，不需要另存一份 result。

新增/改写的 e2e 断言里有两条是**防回归**性质的，值得留着：

- `.diag-block` 里不许再出现「快捷键冲突」「beets 集成」——防止下次有人
  顺手把这两块加回来
- 「整理库四件套」脚本改成先点 `.maint-fold > summary` 再找按钮——折叠
  是默认态，这条测试同时锁住了"默认收起"这个决定

## 6. 仍欠

- **任务登记表**：`job_id + kind + cancellable`，五条线的事件都带 `jobId`，
  前端一个 `TaskView[]`。收益是三件现在做不到的事（互斥可见、安装可取消、
  维护失败不丢）。代价是要动后端事件信封，跟这一轮的纯前端改动不是一个量级。
- **未装 beets 态的自动化覆盖**：mock 里 `beets.found` 恒为 true，
  所以"整段收成一行"只有肉眼验过，没有测试。要补得给 mock 加一个
  `found: false` 的场景开关。
- **`PowerInfo` / `StreamsInfo` 仍在 DTO 里**：UI 不再显示，但后端还在采集。
  留着是对的（日志与将来的自检页还要用），只是别再往主路由上搬。
